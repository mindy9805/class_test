# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | 推測：備貨超過當天實際想買的人數。規則書：報廢 16 份以上要付每份 3 元（超過 5 份部分）再加 50 元清運費 | 查盤點的「報廢」和「賣完後沒買到」，把報廢多的那樣菜備貨降到「賣出＋賣完後沒買到」（盤點建議值），不自行加減百分比 |
| 嫌太貴很多 | 推測：定價超過客人剩下的預算（規則書：價格 ≤ 剩餘預算才買）。需先確認是哪樣菜、哪幾位客人 | 只針對被嫌貴的那樣菜，在可定價範圍內小幅降價；寫明會犧牲每份收益，下一版再用收入和淨利檢驗 |
| 想吃的沒上架很多 | 推測：上架的菜和客人想吃的不一致（最多上架 4 樣，客人最多想吃兩樣） | 把被想吃最多、目前沒上架的菜換進來，換掉賣得最少的菜；同時檢查總份數 ≤ 80、備貨成本 ＋ 宣傳費 ≤ 資金 |
| 因為討厭的菜不進門 | 推測：上架的某樣菜是某些客人討厭的，這些客人直接不進門（也不留評價） | 比較「該菜的收入」和「少掉的客人能買的金額」，不划算就下架；先確認是哪一樣菜造成，不憑印象改 |
| 星等往下掉 | 觀察依據：規則書以進店客人的滿意與不滿比例升降星等（不滿 ≥ 25% 降 0.5 顆、≥ 40% 降 1 顆）；不滿 ＝ 什麼都沒買到。推測：不滿的主因是賣完、太貴或沒上架，需看那天的「沒買到」線索 | 先找出該天不滿最多的原因，再只改對應的那一項（備貨、價格或上架），因為星等會影響隔天的來客數 |
| ★ 我自己發現的現象：宣傳後增加來客，但淨利未改善 | 先核對（實際數字）：新增收入 ＝ 宣傳日收入 − 比較基準日收入；新增成本 ＝ 備貨成本增加 ＋ 宣傳費（200 或 500 元）＋ 清潔費變化。若新增收入 < 新增成本，淨利就不會改善。推測（需驗證）：多來的客人因備貨不足而買不到，或貨備太多造成報廢。注意：來客數也受星等和天氣影響，比較時要說明兩天條件是否相同 | 一次只改一處：先確認新增收入與新增成本的數字；備貨不足就只調那樣菜的備貨，報廢多就降備貨；若宣傳費高於新增收入就回到不宣傳。每次修改後都用試算檢驗 |

> 閱讀這張表時，「推測」是需要用試算數字確認的假設，不是已確認的原因；「觀察依據」才是規則書或試算輸出可以直接對照的內容。

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 不准修改遊戲檔案（`src/` 底下的任何檔案、客人包）
- 只能新增或修改 `web-lab/plans/` 裡的策略檔
